# Phase 3 Slice 1 — Security Review Correction

## Review Finding

Direct authenticated `INSERT`, `UPDATE`, and `DELETE` access to
`public.user_subjects` was unnecessary. Repository-wide inspection found that
the only application `.from("user_subjects")` path is the owner-scoped GET and
post-mutation readback. Membership replacement already uses
`lockdin_replace_user_subjects(...)`, and onboarding already uses
`lockdin_complete_onboarding(...)`. Frontend onboarding and Settings mutations
reach those functions through the Express API; no legitimate UI or application
flow writes the table directly.

The previous write grants exposed a second mutation boundary that could delete
the final membership, bypass the API's 1–5 validation, or select a valid but
non-current syllabus version. Removing that boundary makes the transactional
functions authoritative.

## Final Membership Security Model

- Direct authenticated table access: `SELECT` only.
- Owner visibility: retained through `user_subjects_select_own` and
  `(select auth.uid()) = user_id`.
- Membership mutations: trusted RPC only.
- `PUBLIC` and `anon`: no table privileges.
- Function execution: unchanged; only `authenticated` can execute the
  onboarding and replacement functions.

Supabase's current Data API guidance treats grants and RLS as separate layers
and recommends granting each role only the privileges it needs. This correction
uses both: the table grant blocks every direct write, while RLS limits the
remaining SELECT privilege to the caller's rows.

## 1–5 Invariant

Both trusted functions derive the caller from `auth.uid()`, reject unauthenticated
calls, reject empty, duplicate, invalid, and six-subject inputs, and accept final
sets containing one through five distinct valid subjects. Replacement locks the
caller's profile and performs deletion and insertion in one PostgreSQL
transaction. Its intermediate state is not externally visible; a failure rolls
back the whole mutation. A naive minimum-one DELETE trigger was intentionally
not added because it would break valid atomic replacement.

The `lockdin_enforce_user_subject_limit()` INSERT trigger remains as defense in
depth. Trusted onboarding and replacement stay within five and are unaffected.
A privileged local sixth insert was still rejected with
`user_subject_limit_exceeded`, so administrative or future trusted writes retain
the same ceiling.

Verified final-set behavior:

- `0`: rejected
- `1`, `2`, `3`, `4`, `5`: accepted
- `6`: rejected
- duplicates: rejected
- invalid subjects: rejected without partial state

Verified replacement transitions included `1 -> 5`, `5 -> 1`, `1 ->` a
different one, `5 ->` a different valid five-set, `4 -> 5`, and `5 -> 4`.

## Version Integrity

The composite foreign key still proves that `syllabus_version_id` belongs to
`subject_id`. The trusted functions additionally resolve the unique current
version for every selected subject. Local final-state checks found exactly the
requested distinct subjects, matching subject/version pairs, and `is_current =
true` for every membership. Because authenticated users now lack table UPDATE
and INSERT privileges, they cannot bypass current-version resolution by choosing
another otherwise-valid version through the Data API.
