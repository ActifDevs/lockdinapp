## Source and Import Architecture

Repository source CSVs live under `data/syllabi/raw/`. `scripts/src/syllabus/manifest.ts` maps each supported subject to its CSV, codes, names, board, level, and version metadata. The CLI at `scripts/src/syllabus/cli.ts` reads that directory, validates rows, normalizes the flat records, and invokes the database upsert layer.

```text
data/syllabi/raw/*.csv
  -> version-controlled subject manifest
  -> CSV parsing and validation
  -> normalized units/topics/outcomes/components
  -> per-subject transactional idempotent upsert
  -> shared PostgreSQL reference tables
```

The importer uses explicit column projections and stable natural/reference keys. Each subject import runs transactionally; a failure rolls back that subject without a partial write. Re-running the same validated inputs is idempotent. Phase 3 closeout introduced no new ingestion behavior and did not execute an import.

## Shared Structures

| Table | Pipeline role |
| --- | --- |
| `subjects` | Canonical subject identity and catalogue entry |
| `syllabus_versions` | Versioned syllabus track for a subject |
| `syllabus_units` | Ordered major curriculum units |
| `syllabus_topics` | Ordered topics beneath units; reference data only |
| `syllabus_learning_outcomes` | Granular learning outcomes beneath topics |
| `assessment_components` | Canonical component/paper metadata from the reference source |
| `learning_outcome_components` | Many-to-many applicability between outcomes and components |

These tables are shared by all users. They do not contain personal ownership or progress fields.

## Relationship to Personal Data

| Personal domain | Shared reference relationship |
| --- | --- |
| `user_subjects` | Links a caller to a valid `subject` and current `syllabus_version` |
| `topic_progress` | Links a caller to a shared `syllabus_topic`; stores personal status/notes separately |
| `past_paper_attempts` | Links a caller's attempt to shared subject/component references while storing attempt facts such as year and marks |
| `exam_dates` | Links a caller's planned exam to a shared subject while retaining the caller-owned date/paper details |
| `tasks` | Links a caller-owned task to a shared subject and optionally one shared topic |

The API composes shared syllabus rows with caller-owned rows at read time. When no `topic_progress` row exists, the response reconstructs neutral personal defaults (`status = not_started`, `notes = null`) without mutating the shared topic.
