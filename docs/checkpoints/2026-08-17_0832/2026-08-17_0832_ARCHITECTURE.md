# Phase 3 Architecture

## Runtime Flow

```text
React frontend
  -> Express API
  -> requireAuth / optionalAuth
  -> request-scoped authenticated Supabase client
  -> PostgreSQL Data API or trusted RPC
  -> RLS, grants, constraints, and caller-derived ownership
```

The browser supplies a normal user access token. Express verifies the identity, stores the UUID and token on the request, and creates a Supabase client scoped to that token. Personal routes derive ownership from the verified caller; client-supplied `userId`, `user_id`, `ownerId`, and `owner_id` fields are not trusted.

## Personal Domains

| Domain | Ownership key | Read path | Write path | Isolation boundary |
| --- | --- | --- | --- | --- |
| `profiles` | `profiles.id = auth.users.id` | Authenticated profile API filters by the caller UUID | Profile API and atomic onboarding RPC act on `auth.uid()` | Own-row RLS; profile bootstrap follows Auth creation |
| `tasks` | Required `tasks.user_id` | Authenticated API explicitly filters `user_id` in addition to RLS | API injects the verified caller UUID for create/update/delete | Own-row RLS and server-side owner derivation; owner aliases rejected |
| `user_subjects` | Composite key `(user_id, subject_id)` | Authenticated list filters by caller; Dashboard/progress consume only caller memberships | Transactional onboarding and `lockdin_replace_user_subjects`; direct Data API writes denied | Own-row SELECT RLS, read-only authenticated table grant, trusted RPCs derive `auth.uid()` |
| `topic_progress` | Composite key `(user_id, topic_id)` | Caller rows overlay shared syllabus topics; missing rows become neutral defaults | `lockdin_upsert_topic_progress` and `lockdin_reset_topic_progress` derive `auth.uid()` | Own-row SELECT RLS; direct Data API writes denied; shared topics remain unchanged |
| `past_paper_attempts` | Required `user_id` | Caller-filtered list and subject-performance queries | API injects caller UUID for create/delete; percentage is server-computed | Own-row SELECT/INSERT/DELETE RLS; no client-trusted owner; foreign deletes are nondisclosing |
| `exam_dates` | Required `user_id` | Caller-filtered chronological lists and Dashboard aggregation | API injects caller UUID for create/delete | Own-row SELECT/INSERT/DELETE RLS; no UPDATE privilege or PATCH route; foreign deletes are nondisclosing |

All personal foreign keys to `auth.users(id)` use deletion behavior that removes the deleted user's dependent personal rows. The final hosted cleanup proved this boundary for both retry users.

## Trusted RPC Boundary

The `user_subjects` and `topic_progress` tables expose authenticated reads but not direct authenticated writes. Their `SECURITY DEFINER` RPCs have empty search paths, derive the caller only from `auth.uid()`, validate reference rows and inputs, and grant execution only to `authenticated`. Membership replacement is transactional and enforces 1–5 unique valid subjects. Topic reset deletes only the caller/topic row; a neutral `not_started` state with no notes is not persisted.

## Shared Reference Boundary

The following tables are canonical, shared syllabus/reference data and contain no `user_id` ownership field:

- `subjects`
- `syllabus_versions`
- `syllabus_units`
- `syllabus_topics`
- `syllabus_learning_outcomes`
- `assessment_components`
- `learning_outcome_components`

Personal membership and activity tables reference these shared structures. `syllabus_topics` no longer stores `status` or `notes`; personal progress exists only in `topic_progress`.

## Aggregation and Client Isolation

Dashboard and Progress aggregation use the authenticated caller's profile, memberships, tasks, topic progress, past-paper attempts, and exam dates. `subjectProgressSummary` contains only the caller's current memberships, and shared catalogue placeholders are not interpreted as personal progress.

TanStack Query state is cleared when the authenticated identity changes or signs out. Personal browser-storage values—such as streaks, achievement unlocks, and per-user reminder execution markers—are qualified by user UUID. Global UI preferences may remain global, but personal state is never shared through an unqualified storage key.

## Defense in Depth

- Authentication middleware rejects missing or invalid sessions.
- Routes explicitly scope personal queries to the verified UUID.
- RLS repeats the ownership check at PostgreSQL.
- Restricted grants remove mutation paths that must use trusted RPCs.
- Constraints enforce valid ownership/reference relationships and domain values.
- API contracts omit ownership fields and reject spoof aliases.

Phase 3 is complete on the integration branch only; this architecture is not yet merged to `main` or deployed to managed full-stack Production.
