# Reference Data Pipeline

This document describes the pipeline for parsing, validating, normalizing, and importing Cambridge International A-Level syllabus reference data into the Lockdin database.

---

## High-Level Flow

```text
Official Cambridge Syllabus PDF
        │
        ▼
Extracted CSV File (data/syllabi/raw/)
        │
        ▼
Validation CLI (syllabus:validate) ── [Strict Schema & Header Checks]
        │
        ▼
Normalization Pipeline (scripts/src/syllabus/normalize.ts)
        │
        ▼
Database Importer CLI (syllabus:import) ── [Idempotent DB Transactions]
        │
        ▼
Supabase PostgreSQL Reference Tables
        │
        ▼
Express API Endpoints (/api/subjects, /api/syllabus)
        │
        ▼
React Revision Platform UI
```

## CSV Schema

The pipeline expects a standardized 12-column CSV layout.

| Column Index | Header Name | Data Type | Requirement / Constraints | Description |
| ---: | --- | --- | --- | --- |
| **0** | `Main Topic` | String | Non-empty string | Unit or major module header |
| **1** | `Subtopic` | String | Non-empty string | Specific topic title |
| **2** | `Learning Outcome` | String | Non-empty string | Granular learning outcome statement |
| **3** | `Subject` | String | Non-empty string | Subject title (e.g. `Physics`) |
| **4** | `Exam Board` | String | Fixed: `CIE` | Examination board identifier |
| **5** | `Qualification` | String | Fixed: `A-Level` | Qualification level |
| **6** | `Level` | String | `AS`, `A2`, or `AS/A2` | Curriculum tier |
| **7** | `Component Name` | String | Non-empty string | Assessment component title |
| **8** | `Paper Code` | String / Integer | e.g. `9702/1` | Cambridge paper designation |
| **9** | `Duration (min)` | Integer | Positive integer | Exam duration in minutes |
| **10** | `Total Marks` | Integer | Positive integer | Total raw marks for paper |
| **11** | `Weighting (%)` | Numeric | Decimal percentage | Weighting toward qualification |

## CSV → Database Mapping

The normalization engine parses raw CSV rows into a multi-tiered relational hierarchy.

| CSV Source Column | Database Destination Table | Destination Column | Normalization / Transformation Rules |
| --- | --- | --- | --- |
| `Subject` + `Paper Code` (prefix) | `subjects` | `code`, `name` | Extracted numeric subject code (e.g. `9702` from `9702/1`) |
| `Exam Board`, `Qualification` | `subjects` | `exam_board`, `level` | Fixed enum mapping (`CIE`, `A-Level`) |
| Default `2024-2026` track | `syllabus_versions` | `version_code`, `valid_from_year` | Automatic version tracking per subject |
| `Main Topic` | `syllabus_units` | `unit_code`, `title`, `order_index` | Grouped by unique Main Topic string within subject; order index assigned sequentially |
| `Subtopic` | `syllabus_topics` | `topic_code`, `title`, `order_index` | Grouped under parent unit; order index assigned sequentially |
| `Learning Outcome` | `syllabus_learning_outcomes` | `outcome_code`, `description` | Deduplicated outcome strings mapped to parent topic |
| `Component Name`, `Paper Code`, `Duration`, `Total Marks`, `Weighting` | `assessment_components` | `component_number`, `name`, `duration_minutes`, `total_marks`, `weighting_percent` | Paper Code suffix parsed to integer `component_number` (e.g. `1` from `9702/1`) |
| Junction Mapping | `learning_outcome_components` | `learning_outcome_id`, `assessment_component_id` | Links each learning outcome to its applicable assessment components |

## Import Process Commands

All commands are executed via `pnpm` from the workspace root.

### 1. CSV Schema Validation
Validates all 9 CSV files against schema requirements, checking headers, non-empty text, numeric bounds, and encoding.

```bash
cmd /c pnpm --filter @workspace/scripts syllabus:validate
```

### 2. Dry Run Import
Executes full CSV parsing, entity extraction, structural normalization, and database validation without writing changes.

```bash
cmd /c pnpm --filter @workspace/scripts syllabus:import --dry-run
```

### 3. Production Import
Executes idempotent database import wrapped inside PostgreSQL transactions.

```bash
cmd /c pnpm --filter @workspace/scripts syllabus:import
```

## Import Safety & Integrity Controls

1. **Transaction Atomicity:** Every subject import is executed inside an isolated database transaction (`BEGIN ... COMMIT`). If an error occurs during parsing or insertion, the transaction rolls back cleanly.
2. **Idempotent Upsert Strategy:**
   - Canonical tables (`subjects`, `syllabus_versions`, `syllabus_units`, `syllabus_topics`, `syllabus_learning_outcomes`, `assessment_components`) use `ON CONFLICT DO UPDATE` or key lookups to prevent duplicate rows across repeated runs.
   - Outcome-to-Component links (`learning_outcome_components`) are synchronized cleanly within the subject transaction.
3. **Preservation of Order Index:** Sequential ordering of units, topics, and learning outcomes in the CSV source is preserved explicitly via zero-indexed `order_index` columns to maintain pedagogical structure on the frontend.
4. **Stable Row Counts:** Verified live database totals match expected syllabus metrics:
   - 9 Subjects
   - 136 Syllabus Units
   - 520 Syllabus Topics
   - 3,198 Learning Outcomes
   - 50 Assessment Components
   - 4,817 Learning Outcome Component Links

## Runtime Data Flow

When a student interacts with syllabus data on the client application:

```text
User Enrolls in Subject (e.g. Physics 9702)
        │
        ▼
Frontend Queries API: GET /api/subjects
        │
        ▼
API Server Fetches Canonical Subject & Metrics from `subjects` & `syllabus_topics`
        │
        ▼
User Navigates Subject Units: GET /api/subjects/9702/units
        │
        ▼
Frontend Renders Canonical Units & Topics
        │
        ▼
User Updates Task / Topic Progress
        │
        ▼
API Server Stores Progress in User-Owned Tables (`tasks`) with `user_id = auth.uid()`
(Shared canonical syllabus tables remain read-only)
```
