### Key Directories Explained

**artifacts/api-server/** - Express backend that serves REST API endpoints. Contains route handlers for subjects, tasks, past papers, exam dates, dashboard analytics, and progress tracking. Uses Drizzle ORM for database access and Zod for request validation.

**artifacts/revision-platform/** - React frontend application built with Vite. Contains all UI components, pages, and application logic. Uses Wouter for routing, TanStack Query for data fetching, and shadcn/ui for UI components. Currently uses mock localStorage authentication.

**lib/db/** - Database schema definitions using Drizzle ORM. Contains the canonical data model that drives both backend API types and frontend TypeScript types. Schema has been expanded with syllabus versioning, assessment component atomization, and learning outcome normalization. Migration file ready for deployment.

**lib/db/migrations/** - Database migration files. Contains 0000_syllabus_reference_and_paper_attempts.sql which adds new tables and constraints. This migration requires the cleanup script to be run first to remove placeholder syllabus data.

**lib/api-spec/** - OpenAPI specification that serves as the source of truth for API contracts. Used by Orval to generate React Query client and Zod validation schemas.

**lib/api-zod/** - Auto-generated Zod validation schemas from the OpenAPI specification. Used by the API server for request/response validation.

**lib/api-client-react/** - Auto-generated React Query client from the OpenAPI specification. Provides type-safe API calls to the backend.

**data/syllabi/raw/** - Raw CSV files containing Cambridge A-Level syllabus data for 9 subjects. Files have been validated and are ready for import via the new import pipeline.

**scripts/src/syllabus/** - NEW: Complete import pipeline implementation. Includes CSV parsing, validation, normalization, and transactional database upsert. Provides CLI interface for validation and import operations. Includes unit tests for core functionality.

## Authentication Architecture

### Current Implementation
**Status:** Mock authentication using browser localStorage only

### Authentication Flow
```
User enters credentials in login/signup forms
    ↓
Credentials accepted without validation (any input works)
    ↓
User object stored in localStorage under 'lockdin_user' key
    ↓
Session persisted in localStorage under 'lockdin_auth' key
    ↓
Onboarding status stored in localStorage under 'onboarded' key
    ↓
RequireAuth component checks localStorage for session
    ↓
If session exists, user granted access to protected routes
    ↓
If no session, user redirected to login page
```

### Implementation Details
- **Location:** `artifacts/revision-platform/src/hooks/use-auth.ts`
- **Storage:** Browser localStorage only
- **Validation:** None - any credentials accepted
- **Session Management:** Simple boolean flag in localStorage
- **Password Security:** No password hashing, no secure storage
- **Backend Integration:** None - authentication completely client-side

### User Identity Model
**Current State:** No user identity model exists

**Missing Components:**
- No user table in database schema
- No user registration endpoint
- No login validation endpoint
- No session management backend
- No password reset functionality
- No email verification
- No OAuth integration

### Legacy/Mock Auth Remaining
- **All authentication is mock:** No real authentication implemented
- **No authentication middleware:** API routes completely unprotected
- **No session tokens:** No JWT or session management
- **No password management:** No hashing, no secure storage

### Session Handling
**Current Implementation:**
- Session stored as simple object in localStorage
- No session expiration
- No session refresh
- No concurrent session handling
- No server-side session validation

**Required for Production:**
- Implement JWT or session-based authentication
- Add session expiration and refresh
- Implement server-side session validation
- Add authentication middleware to all API routes
- Implement secure password storage (bcrypt/argon2)

## Database Architecture

### Shared Reference Data

**Status:** Schema implemented with versioning; import pipeline ready

**Reference Tables:**
- `subjects` - Canonical subject catalog (code, name, color) with unique constraint on code
- `syllabus_versions` - Version tracking for syllabus changes (NEW)
- `syllabus_units` - Hierarchical unit structure with version layer
- `syllabus_topics` - Individual topics within units with progress tracking
- `syllabus_learning_outcomes` - Normalized learning outcomes for topics (NEW)
- `assessment_components` - Exam paper components with atomic paper code decomposition (NEW)

**Current Implementation:**
- All reference tables implemented in schema
- Syllabus versioning allows multiple versions per subject
- Assessment components support atomic paper code structure
- Learning outcomes normalized to avoid duplication
- Import pipeline ready to populate these tables

### User-Owned Data

**Status:** Tables defined but lack user ownership columns

**Current Tables:**
- `tasks` - User's revision tasks and deadlines
- `past_paper_attempts` - User's past paper attempts with atomic structure (renamed from past_papers)
- `exam_dates` - User's tracked exam dates
- `syllabus_topics` - User's progress on topics (status field)

**Missing Architecture:**
- No `user_id` or `owner_id` columns on any table
- No user profile table
- No user_subjects table for subject enrollment
- No multi-tenancy support
- All data currently global/shared

**Required for Multi-tenancy:**
- Add `user_id` foreign key to all user-owned tables
- Create `users` table linked to authentication system
- Create `user_subjects` table for subject enrollment
- Implement Row-Level Security (RLS) policies
- Add user context to all database queries

## Data Ownership Model

### Current Model
**Status:** Single-user prototype with no data ownership

**Current Architecture:**
- All tables are global and shared
- No user ownership or isolation
- No multi-tenancy support
- Assumes single implicit user

**Problem:**
- Cannot support multiple users
- No data privacy or isolation
- No user-specific data segregation
- Security vulnerability in multi-user context

### Required Model
**Shared Canonical Syllabus Data:**
- `subjects` - Read-only reference data for all users
- `syllabus_versions` - Read-only reference data for all users
- `syllabus_units` - Read-only reference data for all users
- `syllabus_topics` - Reference structure, but user-specific progress
- `syllabus_learning_outcomes` - Read-only reference data for all users
- `assessment_components` - Read-only reference data for all users
- `learning_outcome_components` - Read-only reference data for all users

**Individual User Data:**
- `users` - User profiles and authentication
- `user_subjects` - User's enrolled subjects
- `tasks` - User's personal revision tasks
- `past_paper_attempts` - User's past paper attempts
- `exam_dates` - User's personal exam schedule
- `syllabus_topics.status` - User's progress on topics (user-specific column)
- `syllabus_topics.notes` - User's notes on topics (user-specific column)

**Implementation Required:**
1. Add `user_id` columns to all user-owned tables
2. Create `users` table linked to authentication system
3. Create `user_subjects` junction table
4. Implement RLS policies for data isolation
5. Add user context to all database queries
6. Separate reference data from user data

**Status:** Atomic paper identity with component/variant/session structure

### Data Model
**Current Implementation:**
```typescript
past_paper_attempts {
  component_id: integer (FK → assessment_components.id)  // NEW
  variant: integer (1-5)  // NEW
  session: enum ('May/June', 'Oct/Nov', 'Feb/Mar', 'Specimen')  // NEW
  // ... other fields
}
```

### Paper Code Structure
**Current Approach:**
- Paper codes atomized into component and variant
- Component stored as foreign key to assessment_components
- Variant stored as integer (1-5)
- Session stored as enum
- Display code generated at read time

**Display Code Generation:**
```
Subject code (from subjects.code) + "/" + paper code (from assessment_components.paper_code) + variant
Example: "9702" + "/" + "42" + "" = "9702/42"
```

**Benefits:**
- Can query by component alone
- Can query by variant alone
- Validation of paper code format
- Relationship to assessment components
- Support for syllabus versioning

### Required Atomization
**Implemented Structure:**
```
Subject (code: "9702")
  ↓
Syllabus Version (subject_id, exam_board, qualification, label)
  ↓
Assessment Component (syllabus_version_id, paper_code: "42", level: "A2", component_name: "A2 Level")
  ↓
Past Paper Attempt (user_id, component_id, variant: 2, session: "May/June", score, total_marks, ...)
```

### Display Code Generation
**Current Implementation:**
- Display code generated from atomic components
- Format: `{subject_code}/{paper_code}{variant}` → "9702/42"
- Atomic components stored, display code generated on read
- Validation of paper code format on write

### Supported Values
**Current Implementation:**
- **Subjects:** 9 Cambridge A-Level subjects (9709, 9702, 9701, 9700, 9618, 9708, 9609, 9489, 9231)
- **Components:** Atomized via assessment_components table
- **Variants:** Integer 1-5 (nullable)
- **Sessions:** Enum ('May/June', 'Oct/Nov', 'Feb/Mar', 'Specimen')

**Validation:**
- Check constraint on variant range (1-5)
- Check constraint on session enum
- Check constraints on score (>= 0, <= total_marks)
- Check constraint on total_marks (> 0)

### Attempt Data Model
**Current Fields:**
```typescript
{
  component_id: integer (FK)  // NEW: Links to assessment_components
  variant: integer (1-5)     // NEW: Paper variant
  session: enum              // NEW: Exam session
  score: real              // Raw score obtained
  total_marks: integer     // Maximum possible marks
  percentage: real         // Calculated percentage
  date_attempted: date     // When the paper was attempted
  time_taken_minutes: integer  // Time spent on paper
  notes: text              // User notes
  created_at: timestamp    // Record creation time
}
```

**Missing Fields:**
- No question-level breakdown
- No topic-level performance analysis
- No difficulty rating
- No confidence rating
- No question-by-question data

### Current Limitations
1. **No user ownership:** Still lacks user_id column
2. **No session management:** Limited session tracking and comparison
3. **No trend analysis:** Cannot track performance across sessions
4. **No predictive analytics:** Cannot predict exam performance
5. **No component-level insights:** Cannot identify weak components (though atomic structure supports this)

### Migration Notes
**Table Rename:**
- `past_papers` → `past_paper_attempts`

**Column Changes:**
- `paper_code` column removed
