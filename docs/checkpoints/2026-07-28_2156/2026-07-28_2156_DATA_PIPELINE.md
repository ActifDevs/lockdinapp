## CSV → Database Mapping

**Status:** IMPLEMENTED

The following mapping represents the actual transformation from CSV columns to database schema as implemented in the import pipeline.

### Current Database Schema
**Available Tables:**
- `subjects` (id, name, code, color)
- `syllabus_versions` (id, subject_id, exam_board, qualification, label, valid_from, valid_to, is_current, source_file, imported_at)
- `assessment_components` (id, syllabus_version_id, paper_code, level, component_name, duration_minutes, total_marks, weighting_percent, order_index, created_at)
- `syllabus_units` (id, subject_id, syllabus_version_id, title, order_index)
- `syllabus_topics` (id, unit_id, subject_id, title, status, notes, order_index)
- `syllabus_learning_outcomes` (id, topic_id, outcome, order_index, created_at)
- `learning_outcome_components` (id, learning_outcome_id, component_id, level, created_at)

### Actual Mapping

| CSV Field | Database Destination | Notes |
|-----------|---------------------|-------|
| Subject | `subjects.name` | Subject name |
| (derived) | `subjects.code` | Extracted from filename (e.g., "9709" from "9709_mathematics.csv") |
| (derived) | `subjects.color` | Mapped from subject catalog in frontend |
| Exam Board | `syllabus_versions.exam_board` | Syllabus version metadata |
| Qualification | `syllabus_versions.qualification` | Syllabus version metadata |
| (derived) | `syllabus_versions.label` | Generated label for version |
| (derived) | `syllabus_versions.source_file` | CSV filename for idempotency |
| Main Topic | `syllabus_units.title` | Creates unit records |
| Subtopic | `syllabus_topics.title` | Creates topic records under units |
| Learning Outcome | `syllabus_learning_outcomes.outcome` | Normalized learning outcomes |
| Level | `assessment_components.level` | Component level (AS/A2) |
| Component Name | `assessment_components.component_name` | Component metadata |
| Paper Code | `assessment_components.paper_code` | Atomic paper code (e.g., "42" not "9702/42") |
| Duration (min) | `assessment_components.duration_minutes` | Component metadata |
| Total Marks | `assessment_components.total_marks` | Component metadata |
| Weighting (%) | `assessment_components.weighting_percent` | Component metadata |
| (derived) | `learning_outcome_components.level` | Junction table for LO-component relationships |
| (derived) | `learning_outcome_components.component_id` | Junction table for LO-component relationships |

### Mapping Implementation Details
**Normalization Strategy:**
- Learning outcomes are normalized to avoid duplication (same outcome text across multiple papers creates one row)
- Junction table `learning_outcome_components` stores many-to-many relationships between outcomes and components
- Component/variant atomization allows querying by component or variant independently
- Syllabus versioning supports multiple versions per subject

**Data Preservation:**
- All CSV data is preserved in the database
- No data loss in the mapping
- Metadata (exam board, qualification, level) stored in appropriate tables
- Component-level details (duration, marks, weighting) stored in assessment_components

### Pipeline Components

**1. CLI Interface (cli.ts)**

**2. CSV Parsing (parse-csv.ts)**

- Data type validation

- Warning generation for non-critical issues

**3. Normalization (normalize.ts)**
- Hierarchical data structure construction
- Unit/topic/outcome relationship building
- Component/variant extraction
- Learning outcome normalization
- Order index assignment
- Notice generation for data transformations

**4. Database Upsert (db-upsert.ts)**
- Transactional upsert per subject
- Bulk operations for performance
- Natural key-based idempotency
- Progress preservation (status/notes never overwritten)
- Detailed count reporting (created/updated/unchanged)
- Automatic rollback on failure

**5. Manifest (manifest.ts)**
- Import configuration for all subjects
- Subject metadata (code, name, color)
- CSV file mapping
- Version labels and metadata

**6. Types (types.ts)**
- TypeScript type definitions
- Normalized data structures
- Import result types

**7. Cleanup Script (cleanup-placeholder-syllabus.ts)**
- Removes placeholder syllabus data before migration
- Prerequisite for migration execution
- Safe deletion with verification

### Performance Characteristics

**Bulk Operations:**
- Existing rows loaded with one bulk SELECT per table
- New rows written with one bulk multi-row INSERT per table
- In-memory diffing to minimize database round-trips
- Avoids per-row SELECT-then-INSERT loop

**Transaction Safety:**
- Each subject import in single transaction
- Atomic operations
- Automatic rollback on failure
- No partial data left in inconsistent state

**Idempotency:**
- Natural keys for all tables
- Upsert logic (insert or update)
- Re-running import is safe
- No duplicate data on re-import
