### Key Directories Explained

**artifacts/api-server/** - Express backend that serves REST API endpoints. Contains route handlers for subjects, tasks, past papers, exam dates, dashboard analytics, and progress tracking. Uses Drizzle ORM for database access and Zod for request validation.

**artifacts/revision-platform/** - React frontend application built with Vite. Contains all UI components, pages, and application logic. Uses Wouter for routing, TanStack Query for data fetching, and shadcn/ui for UI components. Currently uses mock localStorage authentication.

**lib/db/** - Database schema definitions using Drizzle ORM. Contains the canonical data model that drives both backend API types and frontend TypeScript types. Schema is defined but not deployed.

**lib/api-spec/** - OpenAPI specification that serves as the source of truth for API contracts. Used by Orval to generate React Query client and Zod validation schemas.

**lib/api-zod/** - Auto-generated Zod validation schemas from the OpenAPI specification. Used by the API server for request/response validation.

**lib/api-client-react/** - Auto-generated React Query client from the OpenAPI specification. Provides type-safe API calls to the backend.

**data/syllabi/raw/** - Raw CSV files containing Cambridge A-Level syllabus data for 9 subjects. Files have been validated but not imported into the database.

## Authentication Architecture

### Current Implementation
**Status:** Mock authentication using browser localStorage only

### Authentication Flow
```
User enters credentials in login/signup forms
    ↓
Credentials accepted without validation (any input works)
    ↓
User object stored in localStorage under 'lockdin_user' key
    ↓
Session persisted in localStorage under 'lockdin_auth' key
    ↓
Onboarding status stored in localStorage under 'onboarded' key
    ↓
RequireAuth component checks localStorage for session
    ↓
If session exists, user granted access to protected routes
    ↓
If no session, user redirected to login page
```

### Implementation Details
- **Location:** `artifacts/revision-platform/src/hooks/use-auth.ts`
- **Storage:** Browser localStorage only
- **Validation:** None - any credentials accepted
- **Session Management:** Simple boolean flag in localStorage
- **Password Security:** No password hashing, no secure storage
- **Backend Integration:** None - authentication completely client-side

### User Identity Model
**Current State:** No user identity model exists

**Missing Components:**
- No user table in database schema
- No user registration endpoint
- No login validation endpoint
- No session management backend
- No password reset functionality
- No email verification
- No OAuth integration

### Legacy/Mock Auth Remaining
- **All authentication is mock:** No real authentication implemented
- **No authentication middleware:** API routes completely unprotected
- **No session tokens:** No JWT or session management
- **No password management:** No hashing, no secure storage

### Session Handling
**Current Implementation:**
- Session stored as simple object in localStorage

## Data Ownership Model

### Current Model
**Status:** Single-user prototype with no data ownership

**Current Architecture:**
- All tables are global and shared
- No user ownership or isolation
- No multi-tenancy support
- Assumes single implicit user

**Problem:**
- Cannot support multiple users
- No data privacy or isolation
- No user-specific data segregation
- Security vulnerability in multi-user context

### Required Model
**Shared Canonical Syllabus Data:**
- `subjects` - Read-only reference data for all users
- `syllabus_units` - Read-only reference data for all users
- `syllabus_topics` - Reference structure, but user-specific progress
- `assessment_components` - Read-only reference data (not yet implemented)

**Individual User Data:**
- `users` - User profiles and authentication
- `user_subjects` - User's enrolled subjects
- `tasks` - User's personal revision tasks
- `past_papers` - User's past paper attempts
- `exam_dates` - User's personal exam schedule
- `syllabus_topics.status` - User's progress on topics (user-specific column)

**Implementation Required:**
1. Add `user_id` columns to all user-owned tables
2. Create `users` table linked to authentication system
3. Create `user_subjects` junction table
4. Implement RLS policies for data isolation
5. Add user context to all database queries
6. Separate reference data from user data

## Past-Paper Architecture

### Current Model
**Status:** Simple paper code storage without atomization

### Data Model
**Current Implementation:**
```typescript
past_papers {
  paper_code: text  // Stores combined string like "9702/42"
  session: text    // Stores session like "2025-MJ"
  // ... other fields
}
```

### Paper Code Structure
**Current Approach:**
- Paper codes stored as combined strings (e.g., "9702/42")
- No atomic decomposition into component/variant
- Session stored separately
- No component/variant/session tables

**Limitations:**
- Cannot query by component alone
- Cannot query by variant alone
- No validation of paper code format
- No relationship to assessment components

### Required Atomization
**Planned Structure** (not implemented):
```
Subject (code: "9702")
  ↓
Assessment Component (subject_id, component: "4", name: "A2 Level")
  ↓
Variant (component_id, variant: "2", paper_code: "42")
  ↓
Session (variant_id, year: 2025, session: "MJ")
  ↓
Past Paper Attempt (user_id, session_id, score, total_marks, ...)
```

### Display Code Generation
**Current Implementation:**
- Display uses stored `paper_code` directly
- No generation from atomic components
- Format: "9702/42" stored as-is

**Required Implementation:**
- Generate display code from atomic components
- Format: `{subject_code}/{component}{variant}` → "9702/42"
- Store atomic components, generate display code on read
- Validate paper code format on write

### Supported Values
**Current Implementation:**
- **Subjects:** 9 Cambridge A-Level subjects (9709, 9702, 9701, 9700, 9618, 9708, 9609, 9489, 9231)
- **Components:** Not atomized; stored in combined paper code
- **Variants:** Not atomized; stored in combined paper code
- **Sessions:** Stored as text strings (e.g., "2025-MJ")

**Validation:**
- No format validation for paper codes
- No validation of session format
- No validation of component/variant values

### Attempt Data Model
**Current Fields:**
```typescript
{
  score: real              // Raw score obtained
  total_marks: integer     // Maximum possible marks
  percentage: real         // Calculated percentage
  date_attempted: date     // When the paper was attempted
  time_taken_minutes: integer  // Time spent on paper
  notes: text              // User notes
  created_at: timestamp    // Record creation time
}
```

**Missing Fields:**
- No question-level breakdown
- No topic-level performance analysis
- No difficulty rating
- No confidence rating
- No question-by-question data

### Current Limitations
1. **No atomic paper identity:** Cannot analyze performance by component/variant
2. **No session management:** Limited session tracking and comparison
3. **No trend analysis:** Cannot track performance across sessions
4. **No predictive analytics:** Cannot predict exam performance
5. **No component-level insights:** Cannot identify weak components
