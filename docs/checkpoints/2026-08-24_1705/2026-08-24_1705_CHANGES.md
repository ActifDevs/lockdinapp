## Significant Changes

### 1. Global Fail-Secure Authentication Policy (Phase 4 Slice 1)

```text
Change:              Implemented global-by-default API authentication with explicit reviewed method/path exceptions.
Previous State:      Authentication middleware was imported and applied individually by each user-owned router. Any new route mounted without requireAuth would default to being anonymous.
Current State:       app.use("/api", globalAuthPolicy) applies auth to all API routes by default. Only exact reviewed exceptions (healthz, public subject catalogue, optional syllabus auth, and deliberate 403 endpoints) bypass token verification. Unknown or new routes automatically receive 401 Unauthorized unless explicitly exempted.
Reason:              Eliminate the risk of accidental unauthenticated route exposure by inverting the failure mode from opt-in to fail-secure.
Files Affected:      artifacts/api-server/src/express-app.ts

Database Impact:     None. Database schemas, RLS policies, and migrations were not modified.
User-Facing Impact:  No change to valid authenticated user workflows. Public health checks and subject catalogue continue responding 200 without tokens. Protected endpoints securely return 401 if unauthenticated.
Compatibility Notes: Router-level requireAuth and optionalAuth guards were retained as defense-in-depth for isolated router mounts/tests; they short-circuit when identity has already been established by the global policy.
```

### 2. Server-Authoritative Request Correlation IDs (Phase 4 Slice 2)

```text
Change:              Added server-generated UUID request correlation IDs exposed in response headers and correlated with structured Pino logs.
Previous State:      pinoHttp serializers expected req.id, but no middleware populated it, leaving request IDs undefined and untraceable across client/server boundaries.
Current State:       pinoHttp generates a cryptographic UUID per request via crypto.randomUUID(), assigns it to req.id, injects it into the X-Request-Id response header across all HTTP status codes, and ignores client-supplied IDs.
Reason:              Provide end-to-end traceability between frontend error reports, browser network inspector, and backend Pino structured logs during incident investigation.
Files Affected:      artifacts/api-server/src/express-app.ts
                     artifacts/api-server/src/middlewares/request-id.ts (NEW)
                     artifacts/api-server/src/middlewares/request-id.test.ts (NEW - 10 tests)
Database Impact:     None.
User-Facing Impact:  All HTTP responses now include an X-Request-Id header containing a valid UUIDv4.
Compatibility Notes: Client-supplied request ID headers are intentionally ignored to prevent spoofing or log injection attacks.
```
